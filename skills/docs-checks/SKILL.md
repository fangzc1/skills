# 完成检查清单

把项目已有要求写成可判定的**交付契约**，不是收集所有可能有用的检查。

## 决定哪些要求生效

创建时盘点已有交付要求；局部更新只追踪受影响要求及其引用。仓库可以查明的命令和适用范围先自行核实；是否新增门槛、互相冲突的要求如何取舍才需要用户决定。缺少依据的建议留在汇报中，不阻断已确认条目的维护，也不混入生效清单。

## 先找规则来源

读取项目指令、已有完成清单、贡献指南、PR 模板与 CI，核对相关命令定义。区分本地必跑项、CI 专属项和需授权项；CI 中存在某步骤不等于本地必须执行。

目标为仓库根目录 `CHECKS.md`，不使用时间戳。只读核对不写文件；写入限于清单及获准迁移的引用。迁移、汇总或大幅重写先确认，保留用户内容并同步引用；目标被 Git 忽略时报告，不修改 `.gitignore`。

## 每条写成可判断的条件

每项包含：**何时适用 → 做什么 → 怎样算通过**，并能追溯到已确认要求。

例如，项目明确规定某目录改动后进行类型检查，才写入下述结构，并将目录、工作目录和命令替换为已核实的实际值：

```markdown
- [ ] 改动指定目录后，在指定工作目录执行对应类型检查命令，退出码为 0。
```

自动化与人工检查使用同一标准：结果必须可判定。测试方法链接已有测试指南，文档同步引用已有维护规则；不复制操作细节，也不新增覆盖率、发布或迁移义务。

## 完成标准

逐条确认规则来源、适用范围、动作与通过标准；用一个适用改动和一个不适用改动走读条件，确认执行者能判断是否需要检查，而不只是看见复选框。删除重复项，将待确认建议与生效要求分开。清单应要求执行者在完成汇报中明确说明未执行或未通过的项目。

编写清单不等于执行清单。核对命令定义和文档链接即可；若获准试运行，先检查副作用并遵守项目授权，只报告实际执行结果。跳过真实凭证和符号链接内容。

汇报目标文件、核对结果与待确认项，不以文档存在冒充检查通过。
