# UI 规范

记录后续开发应复用什么、为什么某些写法不能照搬，形成现有界面的**约束地图**，不是配置值清单。

## 决定规范覆盖范围

创建时选取公共定义及能覆盖不同主题、布局和组件用法的代表性页面；局部更新只追踪受影响定义与使用方。先查仓库能回答的问题；正式约束冲突或需要确立新视觉规则时才追问。没有足够样本的做法记为局部用法或待确认项，不阻断其他有依据内容的维护。

## 从公共定义到代表性页面

先读项目指令与已有 UI 规范，再查主题、token、公共组件、响应式与暗色模式实现，抽读代表性页面验证实际用法。

目标为仓库根目录 `UI-DESIGN.md`，不使用时间戳。只读核对不写文件；写入限于 UI 规范及获准迁移的引用。迁移、汇总或大幅重写先确认，保留用户内容并同步引用；目标被 Git 忽略时报告，不修改 `.gitignore`。没有实际 UI 或可靠约定时说明缺口，不创建空规范。

## 区分三类信息

- **正式约束**：由已有规范、强制配置或用户确认支持的规则。
- **实际惯例**：多个代表性实现一致采用、但尚未被确认为规则的做法。
- **历史偏离**：具体实现与正式约束的冲突，附位置和已知处理结论。

例如旧页面硬编码颜色，而公共组件使用主题 token，应分别记录权威定义与页面偏离；不能为统一描述而把硬编码提升为规范，也不能在本任务中顺带修改页面。

单个页面的偶然写法不是全局规则。建议单独列出，技术动机未知时写明问题，不把新视觉方向包装成现有规范。

按实际需要记录 token 选择、组件适用范围与扩展边界、主题与响应式限制、项目特有文案约定。链接源码中的权威定义，保留配置无法解释的约束，不抄录完整色板、字号或间距表；技术取舍需要时链接已有决策记录。

## 完成标准

每条正式约束有依据，惯例与历史偏离可定位；用一个代表性组件走读，确认读者能找到公共定义、判断该复用什么以及哪些写法只是局部例外。文档链接和源码路径有效，建议与当前规则分开。

汇报目标文件、核对结果与未覆盖项。遵守项目授权，不为整理规范启动服务或修改界面；跳过真实凭证与符号链接内容。
