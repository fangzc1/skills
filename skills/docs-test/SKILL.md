# 测试指南

写一份能让读者选对测试、准备环境并理解失败的**运行手册**，不是测试框架教程。

## 决定运行手册的范围

创建时覆盖仓库实际存在的测试层次；局部更新核对受影响命令、配置及其用例，不要求重查全部测试。先查仓库可以确认的运行条件；多套测试入口的职责冲突或需要额外权限时才追问。服务不可用、依赖缺失等情况记录为未验证，不阻断有源码依据的运行说明。

## 从实际用例取证

先读项目指令与已有测试入口，再看命令定义、测试配置、fixture 和 CI 的前置服务，抽读每个实际测试层次的典型用例。

目标为仓库根目录 `TEST.md`，不使用时间戳。只读核对不写文件；写入限于测试指南及获准迁移的引用。迁移、汇总或大幅重写先确认，保留用户内容并同步引用；目标被 Git 忽略时报告，不修改 `.gitignore`。没有测试体系或不足以独立成文时说明缺口与建议位置，不创建空壳。

## 写出不明显的运行条件

- **选什么**：各测试层次覆盖什么、在哪里；有命令依据时再提供单文件或单用例的运行方式。
- **怎么准备**：工作目录、服务、fixture、数据准备及环境变量键名。
- **如何隔离**：现有 mock、数据清理和外部服务处理方式。
- **如何判断失败**：记录有证据的跳过、不稳定测试、慢测试及环境限制。失败归因须有错误输出、日志或实现依据，并限定到对应运行或环境；否则只列排查假设，不写原因概率或“所有用例都会失败”等全量结论。

例如脚本名为 `test:unit`，但配置包含真实数据库 fixture，应按配置记录数据库前置条件，不能从“unit”推断测试无外部依赖。

命令定义是权威来源，文档只保留必要入口、选择方法和隐藏前置条件，不复制完整脚本表。将已确认规则与观察到的惯例分开；CI 步骤不自动成为本地要求，运行说明不新增测试义务。类型检查和完成门槛需要时链接已有资料。

## 验证与完成

先确认命令依据，再记录执行状态：

- **依据充分**：仓库脚本、已有运行记录或当前安装版本的帮助／实现支持该命令；框架参数也可依据已确认项目版本的官方文档。核实工作目录、前置条件及参数转发链后，写入运行方式；没有执行时标注“已核对依据，未执行”及原因。
- **依据不足**：只知道 runner 名称，无法确认版本、过滤语法或参数转发行为时，保留已确认的基础入口，将细分运行方式列为待确认项，不给出猜测命令；标注“未验证”不能替代语法依据。

例如仓库只定义 `test:unit` 为 `vitest run`，却没有筛选参数的依据，可以记录该基础入口，说明“单文件／单用例筛选方式待确认”，无需为凑齐运行方式补写参数。

取证不等于执行授权。执行前检查间接脚本及副作用，遵守项目对测试的限制；安装依赖、写库或启动服务需单独授权。失败如实记录，替代命令列出实际执行内容，不冒充原命令通过。配置只记键名，跳过真实凭证和符号链接内容。

当每种已记录的运行方式都有依据、准备条件齐全、惯例与规则区分明确时完成。核对文档链接和源码路径，汇报目标文件、验证结果及未覆盖项。
