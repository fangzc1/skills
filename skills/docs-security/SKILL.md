# 项目安全说明

维护一份有证据的**安全边界说明**，让读者知道系统保护什么、依赖哪些前提，以及哪些风险仍需承担；不是通用安全建议合集或安全认证。

## 决定安全结论的边界

创建时选择约定范围内的主要资产、入口与信任边界；局部更新追踪受影响边界及同类入口，不承诺完成全系统审计。先查安全结论的执行依据；披露范围、正式要求冲突或文档职责冲突需要用户决定。实现不可见、环境未验证等缺口明确标注，继续完成可核实部分，不用默认安全假设补齐。

## 先核实范围与证据

读取项目指令、已有 SECURITY.md 与安全文档入口，再沿相关入口追踪身份认证、权限检查、敏感数据流、外部调用和部署配置。按项目实际形态取证，不为凑齐章节假定存在用户、服务或数据库。

统一使用仓库根目录 `SECURITY.md`，保留已有文档的语言和作用域（不放在 `docs/` 下，不使用时间戳命名）。若该文件仅承载漏洞披露政策，先确认如何在该文件中区分安全说明与披露政策，保留已有政策。大幅重写先确认，用户只要求核对时保持只读。

已有其他位置的安全说明时，先确认迁移或汇总范围，保留内容并同步引用，避免重复维护。只读核对不迁移；标准入口被 Git 忽略时报告并询问，不修改 `.gitignore`。只修改安全说明文档及获准迁移所需的引用。架构全貌和操作细节链接已有资料；没有足够证据时说明缺口，不生成空壳或用框架默认值补齐事实。

## 写清保护措施与成立条件

按实际适用范围组织内容：

- **保护对象与信任边界**：敏感数据、角色、外部系统及数据跨越边界的位置；复杂流转可画 Mermaid 图，附源码或配置路径。
- **威胁与防护**：谁能从哪个入口影响什么资产，现有措施在哪里生效、依赖什么前提，以及剩余风险。只有获得证据的威胁才写为已知问题，合理推演标为待验证。
- **安全设计**：认证与授权、输入处理、数据存储与传输、凭证管理、日志脱敏及依赖边界中实际存在的机制。追踪到执行点，不能因存在中间件或依赖就声称所有路径受保护。
- **安全配置与使用条件**：必要键名、代码中确认的默认行为、部署责任和错误配置的影响。区分项目负责的措施与运行环境提供的保障。
- **已知限制与风险**：受影响范围、触发条件、证据及已有缓解方式；建议与已落实措施分开，未知项写成可回答的问题。

每条安全结论限定到已核实的入口、调用链与环境，注明源码行为、规范要求、用户或运维确认、运行观测与未验证假设等证据来源及范围；依据充分时直接陈述结论。判断访问是否受保护，要核对完整中间件链与挂载顺序：注册点挂了检查不证明检查有效，未挂检查也不证明匿名可达；全量结论需覆盖该范围内所有入口。部署责任归属不证明 TLS 等措施已启用或在何处生效；静态配置也不证明生产状态。

证据不足时写“未核实”，只有明确反证才写“与事实冲突”；未找到控制不等于已证实漏洞。

## 增量维护与敏感信息

认证、权限、敏感数据流、外部信任关系或部署配置变化时，重查受影响边界及同类入口，再精准更新相关段落。代码与已确认安全要求冲突时说明差异并询问，不通过改文档把风险合理化。已有核验日期只在对应范围重新核实后刷新。

仅记录必要键名和脱敏示例，跳过真实凭证、私钥、生产数据及符号链接内容。发现疑似泄露或可利用问题时，向用户私下说明必要定位信息；公开文档只保留适合公开的限制与缓解说明，披露范围未确认前不写入利用细节。

文档维护不授权修复代码、修改安全配置、运行漏洞扫描或攻击性验证，也不授权访问生产系统。需要进一步验证时先说明方法、副作用及所需授权；不自行承诺合规认证、支持版本、响应时限或漏洞报告渠道。

## 完成标准

逐条核对安全结论的证据、适用范围与前提，检查同类入口是否有例外；链接、源码路径和配置键名有效，已落实措施、建议与未知项清晰分离。

汇报目标文件、核对范围、发现的差异与待确认项。明确实际执行的验证与未覆盖范围，不以文档更新或静态阅读宣称系统安全。
