# 架构文档

画一张能帮助读者定位改动的**现状地图**，不是目录清单或理想架构。

## 决定地图范围

新建时选择能解释系统主干的代表性业务链路；局部更新只追踪受影响的运行单元、模块及上下游。深度由边界是否清楚决定，不以遍历全仓库为目标。优先查明仓库可回答的问题；多个系统归属不清或现状与正式约束冲突时才追问，其余缺口标注为未知并继续。

## 追踪后再写

先读项目指令与已有架构文档（统一使用仓库根目录 `ARCHITECTURE.md`，不放在 `docs/` 下，不使用时间戳命名），沿核心业务链路追踪运行入口、模块导出、调用方和外部依赖。每条写入文档的链路追到约定范围内的终点；遇到异步消息或跨进程调用，核实另一端。外部实现不可见时，以已核实的集成边界为终点并标注未知，不用箭头暗示已验证内部行为。

已有其他位置的架构资料时，先确认迁移或汇总范围，保留内容并同步引用，避免维护两份事实。只读核对不迁移；标准入口被 Git 忽略时报告并询问，不修改 `.gitignore`。大幅重写先确认。只修改架构文档及获准迁移所需的引用；没有独立内容可写时说明缺口，不创建空壳。用户只要求核对时保持只读。

## 地图承载什么

- **运行单元**：哪些进程或服务构成系统，如何通信。
- **模块边界**：职责、对外入口、依赖方向，以及改动通常落在哪里。
- **核心数据流**：入口 → 关键模块 → 存储或外部系统，附可定位的源码路径；关系复杂时画 Mermaid 图。
- **重要边界**：有依据的平台差异、特殊处理和容易误判的约束。

import 证明当前依赖，不证明依赖禁令。正式约束要有规范、强制配置或用户确认；未知动机列为具体问题。已有决策记录可链接，未来方案和取舍历史留在各自文档。

例如观察到控制器调用存储适配器，可记录该调用方向及两端入口；只有规范或强制配置支持时，才写成“控制器必须通过适配器访问存储”。

地图记录跨文件才能看清的关系，不抄录文件树、完整导出表或配置值。外部配置仅记必要键名，不读取真实凭证或符号链接内容。

## 完成标准

每个模块职责、调用方向和外部依赖均能对照源码；每条正式约束都有独立依据，图中的每条边已核实或明确标为未知。

检查文档链接与源码路径，汇报目标文件、核对结果及未覆盖链路。遵守项目授权，不为编写文档启动服务或修改业务代码。
