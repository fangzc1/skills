# GitLab MR Skill 设计方案

本 Skill 的目标是简单、高效地创建 GitLab Merge Request（MR），不是合并或发布。最终设计为：**无冲突直接用原源分支提 MR；有冲突从目标创建独立解决分支，只 cherry-pick 用户选定提交。**脚本批量执行确定性步骤，模型只负责范围确认、语义冲突与异常决策。

本文面向维护者，记录需求、失败证据和取舍，不是任务必读。参数、状态与操作规则统一以 [SKILL.md](SKILL.md) 为准；安装及测试见 [使用说明](使用说明.md)，不在本文重复维护第二份执行契约。

## 1. 需求决定的两条路径

用户原始需求是先查冲突，无冲突直接提 MR；有冲突从目标建分支，pick 开发提交、解冲突后提 MR。后续明确：pick 范围由用户选择，未指定就先确认，不自动取全部源独有提交。

| 路径 | MR 实际来源 | 设计原因 |
| --- | --- | --- |
| 无冲突 | 原源分支 | 不制造额外分支与提交，直接交付待评审 MR |
| 有冲突 | 基于目标的新解决分支 | 仅迁移明确选定的需求，不带入环境回流或无关历史 |

两条路径的内容范围不同，不能将选定提交迁移描述为整个源分支已合入。默认只使用本地已提交快照，原工作区和未提交内容不动。

## 2. 架构：按决策点而非逐条命令分工

```mermaid
flowchart LR
    P[preflight：固定快照与本地预检] -->|无冲突| D[deliver：复核、推送、MR核验]
    P -->|有冲突| C[确认统一候选中的选定提交]
    C --> R[resolve：隔离迁移与冲突处理]
    R --> V[最小必要验证]
    V -->|通过| D
```

Git 状态、fetch、候选分类、worktree、Git sequencer、远端核对和 MR 请求由脚本承担，减少模型自行拼接命令和重复查询。模型保留业务判断，不把整个交付串成跨过范围确认或冲突取舍的盲跑。

旧底层接口仅为兼容与回归保留，不应因仍有测试就重新成为任务必经步骤。接口实现看 `scripts/gitlab_mr.py`，不另写一份分页、请求构造或核验字段说明书。

## 3. 冲突检测为何选本地

采用 fetch 目标后对固定快照执行 `git merge-tree --write-tree`：不用切换工作区或先建临时 MR，即可区分文本合并成功、冲突与命令错误。

不采用“先建 MR，再等待服务端判冲突”：GitLab 合并检查异步，`checking/unchecked` 不能被当作已确认无冲突；等待增加往返，还可能留下不需要的 MR。

本地判定只回答当前快照的 Git 合并问题，不证明业务正确、CI 通过或满足所有服务端策略；整分支 merge 的冲突也不等于选定提交逐个 pick 的冲突。残余并发窗口由服务端最终状态与人工审批处理，不用无限轮询或重建来假装消除。

依据：[Git merge-tree](https://git-scm.com/docs/git-merge-tree)、[GitLab MR API](https://docs.gitlab.com/api/merge_requests/)。

## 4. 真实失败：候选必须只有一个事实来源

曾出现 gateway 已以不同 SHA 进入 dev，却被列入“两个都带（推荐）”。原业务仓库的固定本地快照只读复核得到：

```text
- fbbbcc7c8… gateway：补丁等价
+ 91dac71bc… frontend：未找到等价补丁
```

原过滤命令在该快照也能排除 gateway，所以缺陷不能简单归因为“少了一套去重算法”。另一份未过滤的范围日志可能被模型用来重建选项；历史会话目标快照未完整恢复，这一具体偏离路径仍是推断。

最终统一内部分类：预检只给出可解释的 pending/excluded，确认选项只从 pending 生成；执行前复用同一分类，在创建 worktree 前暂停历史等价项。完整分类后才裁剪展示，不把祖先差集数量当待迁移数量。

`git cherry` 与原补丁等价过滤不是两种强弱不同的算法。收益是消除输出旁路及执行前拦截，而非宣称能够识别所有重复业务改动。

补丁等价不能穷尽 squash、冲突改写和语义等价，也不证明改动未被 revert。重新引入 revert 改动需明确意图后另行处理；不引入全库比较、逐提交试 pick 或自动绕过机制。默认不扫描整个目标历史寻找等价 SHA，有争议再定向取证。

## 5. 性能取舍：交付 MR，不做隐式发布认证

此前一段会话约 306 秒仍未交付，包含 60 次 bash 调用；轮间间隔累计约 159 秒，含模型处理与调度，不能全算推理。网络预检约 3 秒，真实冲突、编译和目标基线复现也有明显成本。这不是完整交付基线，不能据此精确估算节省比例。

| 不再默认执行 | 原因 |
| --- | --- |
| 每条机械命令单独组织一轮 | 阶段脚本减少重复查询与模型往返 |
| 无冲突非快进也建验证 worktree | 用户要待评审 MR，不是本地认证可发布状态 |
| 冲突整体 merge 与选定提交迁移双轨 | 用户明确只迁移选定提交 |
| 失败后自动跑目标基线、追完整历史 | 避免验证蔓延；证据不足就如实暂停，不冒称既有失败 |
| 目标变化后反复重建重测 | 单次复检遇新冲突即暂停 |
| 等待 GitLab 状态稳定、细粒度计时 | 不是创建 MR 的必要前置步骤 |

不取消必要验证或仓库明文门禁：人工适配需要覆盖实际行为，不能仅靠空白检查。测试失败、环境缺失等操作边界只在主文维护。CI 配置存在不代表本次实际被验证。

## 6. 命名与溯源的取舍

解决分支采用用户最终指定的“源-to-目标-本地时间”格式，而不是先前讨论的目标/源/时间层级。完整源分支可直接浏览，避免旧逻辑的 selected、目标 SHA 和名称截断丢失来源。

不要求从字符串无歧义反解析分支，不引入额外持久化元数据机制。精确溯源靠初始结果及 MR 描述中的分支、快照和选定提交；继续操作复用原解决分支。具体名称格式统一见主文。

同名与前缀冲突不覆盖、不静默改旧分支。当前未实现独立的平台长度上限检测；Git/远端是否接受极长名称及其错误表现仍需跨平台验证，不能把设计预期当已验证能力。

## 7. 安全机制为什么保留

固定快照、独立 worktree、普通 push、远端 SHA 核验、TLS 与凭据脱敏，是防止错误写入的低成本边界，不为提速去掉。MR 查询/复用及不确定 POST 后先查询，是为了避免重复创建、误报成功；脚本负责这些机械机制，模型无需重新手写 API。

错误恢复规则只在主文和异常触发的 [认证与排错](references/认证与排错.md) 维护。真实语义冲突才按需读取 [冲突处理](references/冲突处理.md)，正常无冲突路径不必加载它们。不会因为文件存在就自动产生读取成本，删文件也不等于已经提速。

## 8. 多模型讨论的裁决

DeepSeek、Gemini、GLM 参与整体流程与候选设计；DeepSeek、GLM、Haiku 参与命名讨论；四者共同评审文档边界。最终并未照单全收：

- 不保留最初的“冲突默认整体 merge”，以用户选定提交迁移需求为准。
- 不全面取消验证，也不将公共契约设为唯一扩围条件；保留风险判断与仓库门禁。
- 不靠强制读取所有参考、增加规则或通用编排器解决慢的问题。
- 不将补丁等价当作业务当前已生效的证明。
- ours/theirs 虽是 Git 术语，但在本次 cherry-pick 语境会影响迁移范围，保留短参考；不将所有特殊文件一律变成确认关卡。
- 设计方案保留失败证据与取舍，不再复制参数和状态契约；重复验证文档删除，API 细节收敛为异常排错。
